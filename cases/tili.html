TILI — 판독문과 수치가 서로 다른 그림을 보고 있었다

병리 분석 결과를 환자까지 잇는 멀티플랫폼 서비스에서, "조용히 틀리는" 지점을 찾아 없앤 기록

기간2026.08
팀5인 (3조)
내 역할추론 워커 · AI 연동
스택Flutter · React · Django · Celery

서비스 한 줄

병리 조직 이미지를 AI가 분석해 면역세포 비율(sTIL)을 수치로 내고, 언어 모델(MedGemma)이 그 결과를 판독문으로 풀어 씁니다. 의료진은 웹·태블릿에서, 환자는 모바일에서 결과를 받습니다. 검체와 환자가 뒤바뀌지 않도록 QR로 본인을 확인합니다.

문제: 두 결과가 서로 다른 것을 보고 있었다

프론트 담당 팀원이 이상한 점을 알려 왔습니다. 화면의 수치는 "종양 0%"인데, 판독문은 종양이 있는 것처럼 읽혔습니다.

직접 따라가 보니 원인은 모델이 아니라 계산 경로였습니다. 수치를 계산하는 쪽과 판독문용 그림을 만드는 쪽이 서로 다른 마스크를 쓰고 있었고, 실제로 재어 보니 AI가 본 그림에는 종양 영역이 5.8% 섞여 있었습니다.

결정: 값을 맞추지 않고, 경로를 하나로

선택지
① 두 결과가 다를 때 한쪽 값을 보정해 맞춘다  ② 계산이 나뉘는 구조 자체를 없앤다
결정
②. 보정은 다음에 또 다른 모양으로 어긋납니다. 마스크를 만드는 함수를 하나(consensus_mask)로 합치고, 판독문 프롬프트에 색상 범례를 넣어 AI가 무엇을 보는지 명시했습니다.
결과
같은 문제가 다시 생기지 않도록 회귀 테스트 7개를 추가했습니다.

원칙: 조용히 틀리느니, 시끄럽게 실패한다

같은 시기에 비슷한 성격의 문제를 두 개 더 찾았습니다.

증상위험바꾼 것
추론 서버가 모르는 모델 이름을 받으면, 오류 없이 더미 모델로 대신 답했다화면에는 정상 결과처럼 보인다요청한 모델과 실제로 쓰인 모델을 비교해, 다르면 즉시 중단
입력 오류(422)가 나면 "오류"라는 말만 남았다원인을 모른 채 재시도만 반복한다서버 응답 본문을 오류 메시지에 담아 원인이 보이게

세 문제 모두 "틀렸는데 틀린 줄 모르는" 상태였습니다. 의료 수치를 다루는 서비스에서는 그럴듯한 오답이 명확한 실패보다 훨씬 위험하다고 판단했고, 이후 워커 코드는 이상하면 멈추고 이유를 말하는 쪽으로 정리했습니다.

팀의 구조 결정

처음에는 클라우드 GPU에서 추론했지만, 비용과 콜드스타트(첫 요청이 느린 문제) 때문에 팀은 로컬 워크스테이션 추론으로 옮겼습니다. 서버가 작업을 밀어 넣는 대신 워커가 작업을 가져가는 방식이라, 외부에서 워크스테이션으로 직접 접속할 필요가 없습니다.

돌아보며
