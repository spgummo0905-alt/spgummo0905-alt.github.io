TILI — 판독문과 수치가 다른 마스크를 쓰던 문제

병리 분석 결과를 의료진과 환자에게 전달하는 멀티플랫폼 서비스에서, 오류가 화면에 드러나지 않던 지점을 찾아 고친 기록

기간2026.08
팀5인 (3조)
내 역할추론 워커 · AI 연동
스택Flutter · React · Django · Celery

01서비스 소개

병리 조직 이미지를 AI가 분석해 면역세포 비율(sTIL)을 수치로 내고, 언어 모델(MedGemma)이 그 결과를 판독문으로 풀어 씁니다. 의료진은 웹·태블릿에서, 환자는 모바일에서 결과를 받습니다. 검체와 환자가 뒤바뀌지 않도록 QR로 본인을 확인합니다.

02문제: 판독문과 수치의 계산 기준이 달랐다

프론트엔드를 맡은 팀원이 이상한 결과를 공유했습니다. 화면 수치는 "종양 0%"였는데, 판독문은 종양이 있는 것처럼 읽혔습니다.

코드를 따라가 보니 원인은 모델이 아닌 계산 경로에 있었습니다. 수치를 계산하는 코드와 판독문용 이미지를 만드는 코드가 서로 다른 마스크를 쓰고 있었고, 판독문용 이미지를 측정해 보니 종양 영역이 5.8% 포함돼 있었습니다.

결정: 마스크 생성 경로 통합

선택지
① 두 결과가 다를 때 한쪽 값을 보정해 맞춘다  ② 계산이 나뉘는 구조 자체를 없앤다
결정
②를 택했습니다. 값을 보정하면 다른 입력에서 다시 어긋날 수 있었기 때문입니다. 마스크 생성 함수를 consensus_mask 하나로 합치고, 판독문 프롬프트에 색상 범례를 넣어 AI가 어떤 영역을 보는지 명시했습니다.
결과
같은 문제가 다시 생기지 않도록 회귀 테스트 7개를 추가했습니다.

03비슷한 오류 두 건 추가 수정

같은 시기에 비슷한 성격의 문제를 두 개 더 찾았습니다.

증상위험바꾼 것
추론 서버가 모르는 모델 이름을 받으면, 오류 없이 더미 모델로 대신 답했다화면에는 정상 결과처럼 보인다요청한 모델과 실제로 쓰인 모델을 비교해, 다르면 즉시 중단
입력 오류(422)가 나면 "오류"라는 메시지만 남았다원인을 모른 채 재시도만 반복한다서버 응답 본문을 오류 메시지에 포함해 원인을 확인할 수 있게 함

세 문제 모두 결과가 틀렸는데도 화면에서는 알아챌 수 없었다는 공통점이 있었습니다. 의료 수치에서는 그럴듯한 오답이 눈에 띄는 오류보다 위험하다고 판단해, 이후 워커 코드는 이상이 있으면 처리를 멈추고 원인을 알리도록 정리했습니다.

04팀의 추론 구조 변경

처음에는 클라우드 GPU에서 추론했지만, 비용과 콜드스타트(첫 요청이 느린 문제) 때문에 팀은 로컬 워크스테이션으로 추론을 옮겼습니다. 워커가 서버에서 작업을 가져가는 방식이어서 외부에서 워크스테이션에 접속할 필요가 없습니다.

05돌아보며

이 프로젝트에서 맡은 일은 대부분 이미 나온 결과를 검증하는 일이었습니다. 앞으로 화면에 숫자를 올릴 때도 그 값이 어느 코드에서 계산됐는지, 틀렸을 때 누가 알아챌 수 있는지를 먼저 확인하려고 합니다.
